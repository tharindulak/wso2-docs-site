# 02 What tools can check MDX for missing components (researched 2026-10-14)

Ticket: [What tools can check MDX for missing components](../issues/02-mdx-lint-tools.md). Input to [What the check enforces](../issues/05-check-rules.md) and the migration map's [Authored-MDX contract and CI check for docs-is](../../wso2-docs-is-migration/issues/08-authored-mdx-contract.md).

Method: npm registry metadata and GitHub API (versions, dates, licences); official docs and READMEs; source of this repo's converter (branch `docs-is-migrate`). Three tools were tried in scratch directories outside the repo (`npm i --ignore-scripts` into a session scratchpad; Vale 3.24.0 macOS arm64 tarball downloaded and its SHA-256 checked against the release's `checksums.txt`), with the same sample rules, then run read-only against the docs-is fork tree (`/Users/admin/Documents/wso2/git/docs/docs-is/docusaurus`, branch `docusaurus-migration`: 6,528 `.md`, 40 `.mdx`). Nothing was installed globally or into this repo. Items marked **[unverified]** are inference or prior knowledge not confirmed in a primary source in this pass.

## Recommendation

Extend `wso2-docs check` with a contract pass: a remark plugin that reads each authored page with the same parser stack Docusaurus uses (remark-parse + remark-mdx + remark-gfm + remark-directive) and reports, with file and line, the hand-written patterns a component covers, unknown components and imports. It adds no new packages (everything is already in the converter's lockfile through `@mdx-js/mdx` 3.1.1), reuses the matchers the convention plugins already have, already emits GitHub annotations, already knows which pages declare `mdx.format: md`, and already runs in the fork's CI through `docs-site/check-action`. Keep Vale in reserve for prose style later; it is now structurally capable but cannot see components or front matter and crashed on one docs-is page. If writers later want squiggles in the editor, publish the same plugin as a remark-lint rule and use vscode-remark, so editor and CI share one implementation.

## 1. remark-lint with remark-mdx (unified-engine, remark-cli)

- **Parsing.** remark-mdx 3.1.1 is the MDX syntax extension from the mdx-js monorepo, the same one `@mdx-js/mdx` 3.1.1 (this converter's compiler) uses, so a `.remarkrc` with `remark-frontmatter`, `remark-gfm`, `remark-directive`, `remark-mdx` parses pages the way the site build does ([npm remark-mdx](https://www.npmjs.com/package/remark-mdx), [npm @mdx-js/mdx](https://www.npmjs.com/package/@mdx-js/mdx)). Directives: `:::note[Before you begin]` becomes a `containerDirective` whose first child carries `data.directiveLabel` ([remark-directive](https://github.com/remarkjs/remark-directive)). Pin remark-directive 3.x to match Docusaurus 3.10 (the converter pins 3.0.1; npm latest is 4.0.0, 2025-02-27).
- **`.md` as MDX.** remark-cli's default extensions are `md, markdown, mdown, mkdn, mkd, mdwn, mkdown, ron` (`markdown-extensions` package); `.mdx` needs `--ext md,mdx`. Plugins in the config apply to every file, so `.md` files are parsed as MDX. The flip side: one plugin set per run. Tried on the docs-is tree, 90 files failed with "Cannot process file" (MDX syntax errors such as a stray `</b>`); these are the pages that declare `mdx: format: md` (95 in the tree). A remark-cli check would need those pages listed in `.remarkignore`, and they would then go unchecked.
- **Custom rule effort.** `unified-lint-rule` 3.0.1 wraps a function `(tree, file) => file.message(reason, node)`; `unist-util-visit-parents` gives ancestors, so "Step heading not inside a `<Steps>` `mdxJsxFlowElement`" is a few lines. The scratch rule (Step headings outside `<Steps>`, Prerequisites heading, Before-you-begin and Deprecated admonitions, unknown capitalised JSX, `mdxjsEsm` imports) was about 20 lines and reported every sample case correctly, with `7:1-7:25` style ranges.
- **Real tree (sizing only, before the one-off rewrite).** Whole `docusaurus/` tree in 49 s wall on an M-series Mac. Reports: 909 `Step N` headings outside `<Steps>` (277 in Latest), 636 Prerequisites/Before-you-begin headings, 627 Prerequisites admonitions, 10 `:::warning[Deprecated …]`, 73 imports (Latest), 668 unknown components. The unknown list shows the allow-list must include components the tree already uses: `ApiReference` (509), `Recommendation`, `Redirect`, `DbConfigTable`, `DatasourceConfig` and others, some of them imported partials. The scratch rule counts headings, not runs; ticket 05 decides the exact rule.
- **Messages and CI.** Default reporter prints `file`, `line:col-line:col`, severity, message, rule id; `--frail` exits 1 on warnings; `--report json` needs the extra package `vfile-reporter-json`. There is no built-in GitHub annotation reporter: convert the JSON (Cloudflare does exactly this for their linter, below) or use `reviewdog/action-remark-lint` (5 stars; avoid).
- **Autofix.** remark-cli can write output (`-o`), but that re-serialises the whole document with remark-stringify, which reformats MDX. Not usable as a writer-facing fix.
- **Editor.** vscode-remark 3.3.1 (2026-06-12) activates on `onLanguage:markdown` (plus prompt/skill languages), so `.md` pages get diagnostics from the repo's `.remarkrc` ([package.json](https://github.com/remarkjs/vscode-remark/blob/main/package.json)). It loads plugins from the workspace, so a writer runs repo code when opening the folder **[unverified: how it interacts with VS Code workspace trust]**.
- **Maintenance.** remark-lint repo last pushed 2026-01-05, remark 2026-09-27; releases are infrequent because the packages are stable (remark-cli 12.0.0 was 2023-09-18).

## 2. markdownlint and markdownlint-cli2

- **No MDX.** markdownlint parses with micromark: CommonMark, GFM, directives (container only; inline directives deliberately off), footnotes, math ([README](https://github.com/DavidAnson/markdownlint#readme)). The maintainer on MDX support: "MDX is not a superset of Markdown … you can't do a single parse and have the output be usable for both", and he does not want to run user code in the parse ([issue #985](https://github.com/DavidAnson/markdownlint/issues/985), closed as not planned).
- **Tried.** Default rules on the sample page: 5 errors, all MD033 "Inline HTML" for `<DeploymentValue>`, `<Tabs>`, `<TabItem>`, `<Steps>`, `<Widget>`. The `import` line and `{expression}` were not recognised as anything.
- **Custom rules.** Rules receive micromark tokens (preferred) or markdown-it tokens, or raw lines (`parser: "none"`), and report via `onError` with optional `fixInfo` ([CustomRules.md](https://github.com/DavidAnson/markdownlint/blob/main/doc/CustomRules.md)). Because a `<Steps>` line is an HTML block that ends at the next blank line, "inside `<Steps>`" has to be tracked by hand across tokens; nested JSX, expressions and imports are not modelled.
- **Fit.** Good for Markdown hygiene (GitLab and GitHub Docs use it); not for an MDX component contract. markdownlint-cli2-action is current (v24.2.0, 2026-08-02).

## 3. Vale

- **MDX status.** "Vale v3.18.0 or later parses MDX natively"; earlier versions needed the external `mdx2vast` on `$PATH`. JSX tags, attributes, ESM and expressions are treated as code; JSX children are linted as Markdown (v3.19+), and "the children carry the element's name as a class scope", so a rule can target `text.class.Steps` ([MDX format](https://docs.vale.sh/formats/mdx.md)). The docs list only `.mdx`; `[formats] md = mdx` in `.vale.ini` made `.md` pages parse as MDX in testing.
- **Structure, not only prose.** Rule types are existence, substitution, occurrence, repetition, consistency, conditional, capitalization, metric, readability, spelling, sequence and script (Tengo) ([llms.txt index](https://docs.vale.sh/llms.txt)). Scopes include `heading.h2`, `list`, `raw` (whole source as one block), negation (`~heading`), class scopes (v3.17+), and since v3.21 `doc(...)` CSS selections over Vale's internal HTML with sections wrapped per heading (`:has()`, `:not()`, `:contains()`; v3.23 adds more) ([Scopes](https://docs.vale.sh/topics/scopes.md)).
- **Tried (3.24.0).** `scope: 'heading & ~text.class.Steps'` with token `^Step \d+(?!\.\d)` flagged the three headings outside `<Steps>` and not the one inside; `heading & ~text.class.Prerequisites` worked the same way; `list & doc(section:has(> h2:contains("next")))` flagged a What's-next list (a `:contains("What's next")` selector with the apostrophe did not match); `:::warning[Deprecated …]` needed a `raw` scope regex with `nonword: true`. On Latest it found the same 277 Step headings as remark.
- **Limits for this ticket.** It cannot see components (JSX is code), so it cannot reject unknown components or imports; it cannot validate lifecycle front matter values; admonitions are text. Vale 3.24.0 **panicked** (goldmark `list.go` interface conversion inside Vale's `mdxIndented` parser) on `versioned_docs/version-5.9.0/setup/changing-to-postgresql.md`, which aborts the whole run with exit 2, not just that file. Worth reporting upstream before relying on it.
- **CI and editor.** `vale-cli/vale-action@v3` (v3.0.0, 2026-08-03; the `errata-ai` org was renamed to `vale-cli`) installs Vale and reviewdog and comments on PRs ([README](https://github.com/errata-ai/vale-action/blob/reviewdog/README.md)); alternatively download the release tarball and verify `vale_<v>_checksums.txt`. Editor support is the `vale-ls` language server; the VS Code client listed is chrischinchilla/vale-vscode ([LSP](https://docs.vale.sh/guides/lsp.md)). One Go binary, MIT, very active (repo pushed 2026-10-14).
- **Fit.** The right tool if WSO2 later enforces a prose style guide (GitLab does). Not the tool for the component contract.

## 4. eslint-mdx / eslint-plugin-mdx

- **What it is.** `eslint-mdx` is an ESLint parser that turns MDX into ESTree (JSX elements, ESM, plus `MDXCode` and `MDXHeading` nodes); `eslint-plugin-mdx` adds the `mdx/remark` rule, which runs the project's remark config (via unified-engine) and surfaces remark-lint messages as ESLint errors, and can lint code blocks ([README](https://github.com/mdx-js/eslint-mdx#readme)). Both 3.8.1, 2026-05-31, MIT, peer `eslint >=8`.
- **`.md` handling.** By default `.mdx` is MDX and `.md` is "plain markdown … linted via remark plugins"; set parser option `extensions` to treat `.md` as MDX. The README notes some options must be set twice (settings and parser options).
- **Tried.** ESLint 9.39.5 flat config with `extensions: ['.md', '.mdx']` and `mdx/remark` running the same scratch remark rule: the same 7 findings, as ESLint errors. ESLint 10 (npm latest 10.12.0) was not tried.
- **Custom rules.** Either ordinary ESLint rules over ESTree (good for JSX: unknown components, attribute checks) or remark-lint rules through `mdx/remark` (needed for headings, lists, directives). So it is remark-lint plus ESLint, not an alternative to it.
- **Fit.** Only worth it where a repo already runs ESLint on content (the content repo does not). 270 packages for what remark-lint does with 250, and the same `mdx.format: md` parse failures.

## 5. Extending `wso2-docs check` (this repo)

What exists (`docs-site/packages/docs-converter`):

- `cli.ts`: `check` converts every page in memory and prints `error`/`warning` lines, or GitHub workflow commands with `--format github` (`::error file=…,line=…,title=wso2-docs <kind>::…`), or JSON; exit 1 on new failures or lifecycle problems. The line comes from a `(line N)` suffix in the error text.
- `page.ts` `compileCheck`: compiles with `@mdx-js/mdx` 3.1.1 and `remark-gfm`, `remark-directive`, a link plugin; CommonMark pages (`format: 'md'`) get `rehype-raw` and `rehypeValidElements`.
- `site.ts` `prepareDocusaurusDocs`: for a Docusaurus-kind source (the docs-is fork) it reads each page, rewrites image and link paths, validates lifecycle front matter (`lifecycle.ts` `checkLifecycle`), honours a page's own `mdx.format: md`, and with `strict` fails pages that do not compile as MDX.
- `html-policy.ts`: regex allow-list (forbidden tags, event handlers, unsafe URLs, iframe hosts) on converted MkDocs pages. The migration map notes it does not run on `docusaurus` sources yet and must before cutover.
- The convention plugins already contain the matchers a contract needs: `remark-steps.ts` (`STEP`, `SUB_STEP`), `remark-prerequisites.ts` (`TITLE` for Prerequisites/Before you begin, heading and admonition forms), `remark-link-cards.ts` (closing-section titles and the "one list of links" shape), `remark-deprecated-sections.ts` with `lifecycle.ts` `isDeprecatedAdmonition`.
- `docs-site/check-action/action.yml`: composite action for content repos, `npm ci --ignore-scripts`, build, `check --format github`; the header says to pin it by commit SHA.

What the extension would be:

1. A `contract.ts` remark plugin emitting `file.message(reason, node, 'wso2-docs:<rule>')` for: Step runs outside `<Steps>`; Prerequisites/Before-you-begin headings or admonitions outside `<Prerequisites>`; a closing link list outside `<LinkCards>`; `:::warning[Deprecated …]` instead of the deprecated form; JSX names not on an allow-list; `import` other than partials. Export the matchers from the convention plugins so the build's recogniser and the check cannot drift (the tree-format decision "one remark plugin for check and build").
2. Run it on the authored source, not on the rewritten text: parse with `unified` + `remark-parse` + `remark-mdx` + `remark-gfm` + `remark-directive`, front matter replaced by the same number of blank lines so positions are source lines. All of `remark-parse` 11.0.0, `remark-mdx` 3.1.1, `unified` 11.0.5, `unist-util-visit-parents` 6.0.2, `vfile` 6.0.3 are already in `packages/docs-converter/package-lock.json`; declare them as direct, exact-pinned dependencies (no new packages).
3. Pages with `mdx.format: md` skip the contract (they cannot host components), or the check rejects that declaration on new pages: a ticket 05 decision.
4. Report a new kind (`contract`) through the existing printer, with severity per rule, so annotations work unchanged. Keep the component allow-list in one exported list that the site's MDX components map also reads.
5. Escape hatch: an MDX comment (`{/* wso2-docs-ignore steps */}`) or front matter key, in the style of today's `stepper: false` / `prerequisites: false` / `link_cards: false` opt-outs.

Effort: about 1 to 2 days with `node:test` tests, mostly rule edge cases (sub-steps, steps inside `<TabItem>`/`<Applies>`, Prerequisites ended by a stepper). Runs in the fork's CI already planned (migration ticket 08) via `check-action`, locally via `npx wso2-docs check`. No editor integration unless the plugin is also published for vscode-remark.

Found while reading (not run): `compileCheck` strips the front matter before compiling and `prepareDocusaurusDocs` regenerates it, so a `(line N)` from a compile error counts from the end of the front matter, not from the top of the source file. Annotations on Docusaurus-kind pages likely land N lines early, where N is the source front matter length. Worth a test when the contract pass is added; parsing the raw source with blanked front matter avoids it for the new rules.

## 6. How others enforce component and markup rules

- **GitLab** (`gitlab-org/gitlab`, [Documentation testing](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/development/documentation/testing/_index.md)): MRs touching `.md` run `docs-lint markdown` = Vale (content), markdownlint (structure) and `scripts/lint-doc.sh` ("page content problems that Vale and markdownlint cannot test for": front matter ownership, filenames, curl long options); plus link, Mermaid and redirect jobs, Vale findings in the MR diff via Code Quality, and `docs hugo_build`, "a partial build of the Hugo website … to validate shortcodes". So component (shortcode) validity is enforced by building, and custom checks live in a script. Vale levels: only `error` fails CI. Writers are told to install the same markdownlint version as CI. Danger: `danger/documentation/Dangerfile` is one call, `documentation.check_documentation` (from the gitlab-dangerfiles gem), a review-routing layer rather than a markup check **[unverified: exact behaviour of the gem method]**.
- **GitHub Docs** ([content linter README](https://github.com/github/docs/blob/main/src/content-linter/README.md), [Using the content linter](https://github.com/github/docs/blob/main/content/contributing/collaborating-on-github-docs/using-the-content-linter.md)): markdownlint with their own `GHD###` rules (front matter, Liquid versioning, code annotations, search-replace regexes), severity `error` (blocks) or `warning` (shown), autofix where possible, disable comments, pre-commit hook. CI (`content-lint-markdown.yml`) lints only changed files with `--errors-only` plus annotations; a weekly job lints everything and files a report. New error rules with many existing violations are rolled out by autofix, disable comments, or warning first. Content is Liquid Markdown, not MDX.
- **Microsoft Learn**: the closed Open Publishing build posts a "Learn Build status" comment on each PR with per-file validation (rule ids such as `disallowed-html-tag`, `ms-topic-invalid`, `code-block-indented`); sign-off requires "no errors or warnings in build validation" ([example PR](https://github.com/MicrosoftDocs/office-docs-powershell/pull/13262)). Writers get the Learn Authoring Pack (Learn Markdown for the custom syntax, markdownlint, templates, YAML schema validation) ([guide](https://learn.microsoft.com/en-us/contribute/content/how-to-write-docs-auth-pack), updated 2024-03-05). Enforcement lives in their build, not an open linter.
- **Cloudflare** (`cloudflare/cloudflare-docs`, Astro/Starlight-style MDX): CI pins every action by full SHA; runs `astro check`, ESLint with reviewdog (not on MDX content), Prettier, `bin/check-component-docs.ts` (component pages and the agent reference stay in sync), and after the build `nimbus-docs lint --format json` turned into `::error` annotations by `bin/nimbus-lint-report.ts`. Structural MDX rules are Semgrep `generic` patterns in `.semgrep/` (for example "footnote syntax inside `<Tabs>`", with a `[skip style guide checks]` commit-message escape hatch); that workflow currently triggers on schedule and dispatch. Unknown components fail the Astro build **[unverified for their setup]**.
- **Pattern.** Each team uses a general linter for hygiene or prose and its own build or script for platform-specific markup. None uses an off-the-shelf MDX linter for component rules. That matches putting the contract in `wso2-docs check`.

## GitHub Actions in the fork

- **`wso2-docs check` (recommended):** `uses: tharindulak/Wso2-Cloud/docs-site/check-action@<full SHA>`; installs from the converter's lockfile with `--ignore-scripts`; annotations already work. Supply-chain gap already noted by the migration map: personal fork and unpublished package; settle owner and release before cutover.
- **remark-cli:** a `tools/lint/package.json` with exact pins and lockfile, `npm ci --ignore-scripts`, `npx remark docusaurus --ext md,mdx --frail --quiet --report json`, plus a short script to emit `::error` lines.
- **markdownlint-cli2:** `DavidAnson/markdownlint-cli2-action@<SHA>` (v24.2.0).
- **Vale:** `vale-cli/vale-action@<SHA>` (v3), or download `vale_3.24.0_Linux_64-bit.tar.gz` and verify the checksum file; run per file or exclude the crashing page until fixed upstream.
- **eslint-plugin-mdx:** `npm ci` of ESLint plus plugin and remark config; ESLint formatter or reviewdog.
- In every case pin actions by full commit SHA, not tag: the March 2025 `tj-actions/changed-files` compromise retargeted tags (CVE-2025-30066, [GHSA-mrrh-fwg8-r2c3](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3)); GitHub Docs and Cloudflare both pin by SHA. Give the lint job `permissions: contents: read`; reviewdog-style PR comments additionally need `pull-requests: write`.
