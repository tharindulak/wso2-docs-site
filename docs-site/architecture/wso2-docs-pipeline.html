WSO2 Docs Pipeline

How the new docs site turns each product team's own repository into one Docusaurus site with one navigation, where cloud and self-hosted content live together on the same pages.

What happens on a build

  1. Pin. content-sources.yaml names every section's repo, the commit it is pinned to, the branch the bot follows, its default deployment options and its exclude list.
  2. Fetch. Only the docs folders of exactly those commits are downloaded into .cache/sources.
  3. Convert. MkDocs pages are rendered, merged (Identity's Asgardeo and Identity Server pages become one page with labelled differences), checked against the HTML allow-list, rewritten to MDX and compiled. Docusaurus pages are copied with labels and link fixes.
  4. Assemble. Sidebars come from each repo's own navigation. Cloud doc sets are placed inside their product: Devant inside WSO2 Integrator, Bijira inside API Manager.
  5. Build. Docusaurus reads generated/manifest.json, creates one docs section per product section and renders the Oxygen look, Products menu, product bar and deployment box.
  6. Stay current. The bump bot moves pins hourly through auto-merged PRs; promotions to a new release need approval; teams run the same check on their own PRs.

Known gaps in this picture

  • The Docusaurus lane skips the HTML allow-list, and evaluating sidebars.ts runs the content repo's code at build time. Both need a security review before bumps auto-merge.
  • Custom MkDocs page templates (quick-start, complete-guide, SDK) and the 245 API reference pages have no layout in the site yet.
  • Search is a placeholder until the Algolia DocSearch legal review is done.
  • The workflows have not run yet: this repository has no GitHub remote.
